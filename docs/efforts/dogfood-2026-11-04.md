### S1 — Swipe-delete crash on Workbench and Menu

**What's known.** Deleting a workbench and deleting a menu both crash, neither on the last row, on the Active tab for
workbenches. The iPad's three reports from 2026-11-04 (`YesChef-2026-11-04-101126`, `-101153`, `-124803`; build 1218,
iPadOS 27.0.1) are the same `SIGABRT` from
`-[UICollectionView _Bug_Detected_In_Client_Of_UICollectionView_Invalid_Number_Of_Items_In_Section:]`, under
`UICollectionViewListCoordinatorBase.performUpdates`. A SwiftUI `List` diff disagreed with its row count. This isn't a
database failure, and the stacks hold no app or GRDB frames.

**The likely cause.** Both lists use `Button(role: .destructive)` in `.swipeActions`, but only open a
`confirmationDialog`; the row leaves the data later. The role tells the list the row is going away now. The Archived
Recipes list had the same crash, and `c77269c` (2026-08-03) changed its button to a plain `Button` with `.tint(.red)`,
the form it still uses. This hasn't been reproduced in isolation, so the device gate is the proof.

**Build.**
1. Remove `role: .destructive` and add `.tint(.red)` on swipe buttons in a `List` that only open a dialog:
   `MenuViews.swift:15`, `WorkbenchViews.swift:98`, `RecipeLibraryView.swift:517` (Delete…), and
   `GroceryViews.swift:656` (delete list). Check the other `List`-hosted `.swipeActions` destructive buttons. A button
   that deletes in its own action keeps the role, and so can rows in non-`List` swipe containers. Add a one-line comment
   at each changed site, in the style of the existing invalid-batch-update comments.
2. While there, make `areWorkbenchRowsInIncreasingOrder` a total order with a final `id` tiebreak. It's the same crash
   family (`RecipeModels.swift:241`), though it needs an exact tie and doesn't explain this crash. Add a package test.

If the crash survives, pull the new report and go again; don't add more speculative changes.

### S5 — Drop feedback and the wrong-day fallback

**Is the missing animation normal?** Not as documented. Apple's reorder guidance says the system shows a reorder gap
as a drag moves between children of a `reorderContainer`. Its examples drop the same type the container reorders; ours
reorders `MenuItemRowData` and drops `MenuDraggedRecipe`. That's the likely reason there's no gap, but it isn't proven.

**A related bug, from the code.** `MenuDetailSections.swift:131`: when `reorderDestination` is nil, the recipe lands on
`max(dayCount - 1, 0)`. On a 7-day menu, a drop that misses a row can land on Day 7, whichever day it was over.

**Build.**
- Add `.onDropSessionUpdated` (iOS 27) to the same container. `DropSession` has `phase` and `location`, and
  `reorderDestination(for:in:)` may give the live day during hover. Keep hover state in the view and highlight the
  target day's section with a tint and stroke. Clear it on `.exiting` and `.ended`.
- Resolve the nil fallback from the hovered day, using `location` against day-section frames if needed. Dropping on an
  empty or collapsed day must land on that day.
- **Don't add a per-day `.dropDestination`.** ADR-0055 Finding 6: stacked destinations shadow each other, and that's
  what broke dish dragging before. The `isTargeted:` overload also loses the `DropSession`.
- Reorder logic stays in pure functions with tests; hover state stays in the view.

If `reorderDestination` is nil during hover and frame matching gets fiddly, land the correct-day fallback and a
whole-list highlight, then say so in the PR.

## Held out: Serve With

**What it is today.** It began as AI output: the Serve With verb generates accompaniment ideas, and ADR-0048 turned
that blob into `recipeServeWith` rows (`title`, `note`, `sortOrder`, `provenance`). Hand-typed Add came along with the
rows. The rows also feed recipe chat. Nothing connects them to the library, so a pairing you already own a recipe for
is a dead label, while Related Recipes links recipes but carries no note and has no sense of "goes with".

**Decided (Jon, 2026-11-04): an optional recipe link on each row.** Rows stay free text ("crusty bread" is a fine
answer), and the editor gets "Link a recipe". Reuses `RelatedRecipePicker` (private today, so extract it). A linked chip
opens the recipe; the title stays as a snapshot. AI suggestions and chat context stay as they are. Dropping hand-typed
entry would leave the dead-label problem in place, and folding into Related Recipes doesn't fit: those edges are
symmetric with no free text or note.

**Persistent model change** (per AGENTS.md):

- **Changing:** add a nullable `linkedRecipeID TEXT` to `recipeServeWith`. It's a soft reference with no FK, like
  `recipeRelatedRecipes`. If the recipe is deleted, the row falls back to plain text.
- **Existing data:** unaffected; every row starts unlinked.
- **Migration:** one append-only `ADD COLUMN`.
- **Sync:** this is a synced table, so the field needs a Development schema change, a Production deploy before any
  TestFlight build carries it, and a `cloudkit-expected-fields.txt` update. Jon merges it (ADR-0005 D9).
- **Also check:** recipe transfer and snapshot paths, import, and adjustment (`RecipeRepository+Import`, `RecipeCore`,
  `RecipeAdjustment`, `RecipeEnrichment` all touch the type), so the link survives them.

**Next step.** ADR-0062 and its own brief, in a separate plan PR, after `launch-data-passes` merges, because both edit
`Schema.swift` and `CloudSync.swift`. An "add this pairing to the menu" action is a possible follow-on; it's not in scope.
