# Review — ADR-0014 D3 + D2, recipe text markup (PR #254)

Review date: 2026-07-28. Reviewer: Claude Code (architect).
Scope: `codex/adr-0014-d3-d2-markup-text` (`f091917`, `f37e075`, `96c742b`) against
[ADR-0014](../decisions/ADR-0014-recipe-text-editing-model.md) D2 (Markdown in free-text fields)
and D3 (`[square bracket]` author notes).

Method: diff read, ADR conformance, full test + build certification, and a **whole-library audit**
against the live backup `YesChef-Backup-2026-07-28.sqlite` (2,179 recipes / 26,932 ingredient lines) —
the same measure-don't-guess method Amd-1 used to settle the colon rule.

## Verdict

**Approve the mechanism; merge with follow-ups.** The device-review fix
(`.inlineOnlyPreservingWhitespace`) is the correct call and is now *proven* correct on real data, not
inferred: every non-empty prose field in the library round-trips through the new render path
byte-for-byte. The residual findings are one silent data regression, one path that bypasses the
change, and three completeness items. None of them justify holding the branch.

**The prose audit is the load-bearing one.** All 455 non-empty `summary` / `makeAhead` / `chefItUp` /
`recipeNotes.text` / `sourceNotes` values were parsed with the exact options the view uses; not one
character was consumed. Specifically, Jon's footnote-asterisk convention survives —

```
*Note: If colossal shrimp are not available… **Note: To coarse-grind the peppercorns…
```

— because neither `*` has a valid right-flanking partner, so CommonMark leaves both literal. This is
the case that would have been quietly corrupted by a naive `.full` parse, and it appears in 14 notes.

## Findings

### F1 — `[OPTIONAL]` ingredient lines silently lose their flag ⚠️ *(fix before merge)*

[`IngredientParser.swift:178`](../../YesChefPackage/Sources/YesChefCore/IngredientParser.swift#L178)
moved the optional check from `text` to `parsed.parsingText`, which excludes bracket spans. Two rows
in the live library are exactly this shape and are **currently `isOptional = 1`**:

```
¼ lb. ground pork [OPTIONAL]
1 tsp ground sichuan peppercorns [OPTIONAL]
```

On the next save of either recipe the flag flips to `0` with no signal. D3 requires brackets to stay
out of **quantity, unit, item, preparation** — `isOptional` is not on that list, and "optional" as a
parenthetical aside is the most natural way a cook writes it. This is the silent-loss shape
ADR-0040's lossless-or-loud rule exists to prevent.

**Fix:** keep `isOptional` reading the full `text`; leave the four parsed fields on `parsingText`.

`doNotShop` moving to `parsingText` is the opposite — a genuine **improvement**. It is an exact
whole-string match, so `kosher salt [Diamond Crystal]` now correctly stops being shopped.

Adjacent, same file: [`IngredientParser.swift:175`](../../YesChefPackage/Sources/YesChefCore/IngredientParser.swift#L175)
still falls back to raw `text` for `canonicalName`, so brackets leak into the canonical key whenever
`item` is nil. Should be `parsed.parsingText`. (`isHeader: text.hasSuffix(":")` is left alone
deliberately — Amd1-D1 rewrites it.)

### F2 — The bracket convention is already occupied — **✅ accepted as-is (Jon, 2026-07-28)**

Recorded because the measurement matters later, not because anything needs doing.

D3 assumed `[…]` means "a Jon note." In the live library it mostly does not. **83 ingredient lines
across 27 recipes carry brackets — all 83 shoppable, none currently carrying a `comment`** — and the
contents are overwhelmingly publisher metric equivalents:

`140g` · `60 g` · `4 cm` · `480 ml` · `1-oz.` · `about 14 oz.` · `230 g` · `click for printable recipe`

Those now populate `comment`, which
[`GroceryCore.swift:1001`](../../YesChefPackage/Sources/YesChefCore/GroceryCore.swift#L1001) joins
into `groceryNotes` — so the grocery list gains "· 140g" annotations (and one
"· click for printable recipe"). Subdued rendering of a metric equivalent is arguably a feature.

**Decision: live with it and see how it feels in use.** Revisit only if the grocery notes read as
noise on a real shop. The number to remember is 83 lines / 27 recipes.

### F3 — Web capture bypasses the change entirely

[`ParsedRecipePage.swift:252`](../../YesChefPackage/Sources/YesChefCore/WebRecipeCapture/ParsedRecipePage.swift#L252)
is the only site that hand-builds `IngredientLine` instead of calling `IngredientParser.lines` — it
drops `comment` and still reads `isOptional` off raw text. Every other construction path (Paprika
import, editor section reconcile, recipe adjustment) goes through `.lines`.

Consequence: a captured recipe parses one way, then re-parses **differently** on its first editor
save — `canonicalName` shifts and `comment` appears, which quietly moves grocery grouping for that
recipe. Capture is the primary import route, so this is where most bracketed lines will actually
arrive.

**Fix:** route it through `IngredientParser.lines`, or at minimum mirror `comment` / `parsingText`.

### F4 — The new test does not test the new code

`RecipeTextMarkupTests.inlineMarkdownPreservesProseLineBreaks` asserts *Foundation's* behavior using
hand-written parsing options. The policy it is meant to protect lives in the app target at
[`RecipeTextViews.swift:19`](../../YesChefApp/RecipeTextViews.swift#L19) — so reverting that view to
`.full` re-breaks Make-ahead's bullets **with the suite still green**. That is the exact defect this
commit was written to fix, left uncovered.

**Fix:** move the policy into Core (`RecipeProseMarkdown.attributed(_:)`), have the view call it, and
point the test at that. Same move gets the rendering rule into the macOS-ready layer, and gives F6 a
home.

### F5 — Missed render site

[`WorkbenchViews.swift:740`](../../YesChefApp/WorkbenchViews.swift#L740) still renders
`recipe.summary` through a plain `Text` — literal `**` will show on the workbench card. ADR-0014 D2's
own consequence line ("anything that displays `summary`/notes must render through the Markdown path")
makes this a completeness item.

Same class, lower stakes: bracket subduing lands only on the recipe-detail row. The grocery
ingredient-choice row ([`GroceryViews.swift:1051`](../../YesChefApp/GroceryViews.swift#L1051)) and
Workbench Compare ([`WorkbenchCompareView.swift:539`](../../YesChefApp/WorkbenchCompareView.swift#L539))
show brackets at full weight. Acceptable for a render-only convention; worth knowing it is not
uniform.

### F6 — New code lands already deprecated (surfaced by the build)

```
YesChefApp/RecipeTextViews.swift:41: warning: '+' was deprecated in iOS 26.0:
  Use string interpolation on `Text` instead
YesChefApp/RecipeTextViews.swift:43: warning: (same)
```

`IngredientLineText` composes its subdued-bracket rendering by `reduce`-ing `Text` values with `+`.
It compiles and works, but it is new code on the deprecation path. The modern form is to build the
segments into a single `AttributedString`, applying the secondary style to author-note runs, and
render one `Text`. Folds naturally into F4: with both the Markdown policy and the segment→
`AttributedString` assembly in Core, all of this markup behavior becomes package-testable instead of
untested app-target view code.

(The other build warnings — `AppNavigationHelpers`, `WorkbenchModels`, `RecipeChatWorkspace` — are
pre-existing and not from this branch.)

## Do the outboard hand-off prompts need to change? **No — and that is now a load-bearing decision.**

Checked against [ADR-0038](../decisions/ADR-0038-external-llm-handoff.md) /
[ADR-0042](../decisions/ADR-0042-workbench-handoff-and-the-return-block.md).

**Outbound: works unchanged.** Recipe prose is interpolated verbatim into the prompt, so `**bold**`
arrives as literal asterisks that any receiving model reads as Markdown. Nothing to escape, nothing
to strip.

**Inbound: leave the ban in place.** Six prompts currently say some form of "no Markdown emphasis"
([`AIHandoffContext.swift`](../../YesChefPackage/Sources/YesChefCore/AIHandoffContext.swift) lines 96,
116, 165, 264, 376, 425). The tempting read after D2 is "prose fields accept markup now, so relax it."
**Don't.** Those returns are not free prose — they are label-parsed line formats: `When: task`
(make-ahead), `title: note` (Serve With), one-action-per-line (`lineListFormat`). The ban is
protecting the *parsers*, not house style. It stopped being a preference the moment those formats
shipped, and the ADR should say so rather than leaving it looking like leftover fussiness.

The honest framing: **D2 markup is a human authoring affordance, not an AI one.** Jon types `**` in
the editor; the models keep returning clean parseable lines. That boundary is consistent with
[ADR-0040's](../decisions/ADR-0040-editable-at-the-grain-it-is-stored.md) "store at the grain you edit" and with the
existing rule that structural rows (ingredient lines, instruction steps — including
`WorkbenchDraftRecipe`'s JSON arrays) never carry markup, since nothing renders it there.

### But: the label matchers are markup-fragile, and that is a real pre-existing bug

Not caused by this PR — worth fixing while the context is loaded, and **before** anyone relaxes an
emphasis ban. `isLearningsMarker`
([`AIHandoff.swift:994`](../../YesChefPackage/Sources/YesChefCore/AIHandoff.swift#L994)) already trims
`#` and `*` before comparing, so `**YC-LEARNINGS:**` survives — someone clearly got burned once and
hardened exactly one site. Every other label matcher was left naive:

| Matcher | Location | Breaks on |
|---|---|---|
| `YC-CONTRACT:` | `AIHandoff.swift:607` | `**YC-CONTRACT: v1**` |
| `YC-HANDOFF:` routing header | `AIHandoff.swift:565` | `**YC-HANDOFF: …**` |
| `tip:` (reader feedback) | `AIHandoff.swift:931` | `**Tip:** …` → tip silently dropped |
| `session:` (prep plan) | `MenuPrepPlan.swift:620` | `**Session:** …` |
| `note:` (menu complement) | `MenuComplement.swift:122` | `**Note:** …` |

A ChatGPT reply that bolds its labels — which is its default habit, ban or no ban — silently loses
those items. Same parser-floor shape as the queued `learningBullets` naked-sentence bug.

**Fix:** one shared helper that trims `#*_` plus whitespace before every label compare, applied at all
five sites. Cheap, retires the class, and belongs with the `learningBullets` tolerant-extraction work
rather than with ADR-0014.
