- [ADR-0042](ADR-0042-workbench-handoff-and-the-return-block.md) — **The workbench hands off; the return block is a terminal turn.** Extends ADR-0038 by adding `.workbench` as a hand-off source and by writing down the return-payload contract ADR-0038 left implicit. Three rules: **(D1)** the conversation is unconstrained, but the turn that emits `YC-HANDOFF:` behaves like a **function return, not an interlocutor** — every failure so far (the S2.5 blob-report: headings, nesting, "what the recipe already does well") was the model never being told to switch modes; **(D2)** *outboard deliberation, keep structured canonical writes in-app* — a bad advisory line costs one delete, a wrong ingredient identity silently corrupts a recipe and orphans ADR-0021 variation anchors, so `adjustRecipe` **stays an unwired placeholder**; **(D3)** prose is welcome exactly where it terminates in a human-read text field, and must be pinned wherever it feeds typed fields. **(D4)** the contract **leaves the payload entirely** and lives in the chat app's **project custom instructions** — generated from one Core constant, pasted via a Settings copy button, with a `YC-CONTRACT: v<n>` marker echoed in the return so a stale or missing paste fails *loudly* instead of silently drifting from the parser; one shared "Yes Chef" project to start, since a menu has a natural end and needs no per-source anchor. This also closes a real structural gap: `.immediate` prompts carry a literal format example, `.discuss` prompts carry **one sentence and no example** — which is the ADR-0041 S2.5 blob-report root cause, routed around but never fixed. Workbench deliverables: **compare** = named differences with a claim attached (never a per-recipe walkthrough — the matrix does that better), **experiments** = `{hypothesis, change, rationale}` → `workbenchLog` rows (**supersedes ADR-0019 S3's `experiments` BLOB** — the `Menu.prepPlan` defect again), **draft** deferred as a structured write. The log is how thinking returns now that there's no reopen link (D6). **Retires ADR-0023 S3's in-app refine loop** as unwanted, not unscheduled (D7). **S1 is schema-free** (`AIHandoff` is device-local; `workbenchLog` already exists); **S2 adds three nullable synced `workbenchLog` columns** — `hypothesis`/`change`/`rationale` — because an experiment is **write-many** (its `outcome` is filled in later) and ADR-0040 puts human-repairable content in typed fields, **not** smeared into `body` (OQ2, resolved 2026-07-20: pre-prod is the reason to fix the shape *now*, not a licence to defer it; contrast ADR-0041's withdrawn `PlaybookSectionMeta`, which failed on *justification*, not cost). **Hand-validated end-to-end (OQ6, 2026-07-20): all slices un-gated.** With the v1 contract living only in the project's custom instructions, a long real conversation switched cleanly into the return block on `finalize`, echoed `YC-CONTRACT: v1`, and held all three field labels — confirming D1/D4/D8 in the shape we'd ship. **One binding failure: blank lines between blocks did not survive the paste path**, so the parser splits on the **label cycle**, never whitespace. **(D9)** threads carry a derived `<TaskType>: <Object>` title — task, not object-kind, since ADR-0041 section-scoping gives one recipe three live threads — and the title is **advisory only** (the auto-titler paraphrased it in testing; nothing parses it). Also **D8: the experiments verb emits no learnings** — 3 of 4 returned "learnings" were its own untested hypotheses restated as fact, which is structural (a conjecture establishes nothing), so knowledge is recorded later in the experiment's `outcome` — an experiment is a *pending* learning (Accepted 2026-07-20; S0/S1 dispatchable, S2 the schema slice behind them)
- [ADR-0032](ADR-0032-workbench-reference-material-fetch.md) — **Workbench reference material, fetched app-side.** Workbench chat context is a static serialization of already-stored data — the model never sees the **source page**, and the cook cannot point the discussion at a URL that isn't a candidate. The naive fix (put the URL in the prompt and tell the model to read it) is **rejected**: with no tool the model hallucinates plausible recipe content, the one unacceptable failure for a fidelity-first app. Each provider's **native server-side web tool** is also rejected as the mechanism — it means three mechanisms behind one flag (Anthropic tool / OpenAI tool / on-device none), it cannot reach **gated** sources (the Milk Street login wall, [[paywall-gating-taxonomy]]), and it hands the fidelity boundary to the provider; **doing the fetch ourselves is the LLM-agnostic implementation and the only one that solves gating.** So: a per-workbench **reference list** (URL → fetched by our own engine (ADR-0007), **reduced** to readable text, cached CompareAlignment-style; or **pasted text** as the gating fallback), injected as **plain grounded text** behind the frontier budget, deduped against candidates, trimmed first on-device. Advisory **read** only — never grocery, pantry, or any persisted recipe field ([[llm-vs-determinism-surface-boundary]]); fetched web text is **data, never instructions**. Reuse not rebuild: fetch (ADR-0007) + reduce (existing editorial-prose extraction) + cache (ADR-0022 pattern) + inject (`WorkbenchChatContext`). S1 model + fetch/reduce/cache core, S2 chat-context injection, S3 list UI + login-wall→paste-in fallback; LLM reduce pass, candidate-source prose and `web_search` discovery all parked (**Accepted 2026-07-23 — but ratification covers the Decision only; its six open questions still need a scoping session (OQ5 has no recommendation) and the slice plan remains proposed. - [ADR-0046](ADR-0046-sidebar-adaptable-app-shell.md) — **The app shell becomes a sidebar-adaptable `TabView`.** Nothing ever *decided* the current three-column `NavigationSplitView` — a `grep -ri docs/` finds no ADR covering app-level navigation; it is the default iPad idiom arrived at by inertia, so this is a first decision, not a reversal. - [ADR-0047](ADR-0047-llm-capture-fallback.md) — **Capture escalates to an LLM extractor when the page carries no machine contract; capture pills are rejected.** The capture path has contained **zero model calls** since ADR-0007 — six deterministic extractors over two rungs (static HTML, and ADR-0009's rendered logged-in DOM), both of which assume the page ships a contract. The triggering page proves the gap: Samin Nosrat's Substack has **no JSON-LD, no microdata, no hRecipe** (verified live) so three extractors miss outright and `warnings` returns `[.noStructuredRecipeData, .noIngredients, .noInstructions]` — yet the HTML is clean and semantic, ingredients in `<ul>`s under two named subheads, directions as numbered steps. Not a hard page: a page with **no contract**, which is the whole category the ladder structurally cannot serve and is most of the food writing worth capturing now. **(D1)** the model is **rung 3 gated on the warnings the parser already computes** — the escalation predicate already exists and is named, so contract-bearing pages (NYT, Milk Street, any plugin blog) never reach it; never LLM-first and never LLM-to-double-check, because a model that can overrule a contract can corrupt a clean capture. **(D2) pills are rejected, not deferred** — they exist in Paprika *because Paprika has no LLM*, `RecipeCaptureView` is already a fully editable review form over the exact same fields (so pills are a **second** correction surface for the same misses), and they are the more expensive build with the worse outcome; *selection-to-field* is parked as a **repair tool for the model's misses**, not a primary path. **(D3)** the model's input is a **structure-preserving serialization, never `bodyText`** — `cleanedBodyText` calls `.text()` and whitespace-joins, which is harmless when a contract carried the structure but fatal here, where the `<ul>`/`<ol>`/`<h#>` structure **is** the recipe boundary; flattening it and asking the model to recover it is asking it to redo what the DOM already did, and this is the way a naive build fails while looking like a model-quality problem. **(D4)** output lands in the **existing** `ParsedRecipePage` — its ingredient/instruction sections already carry an optional `name`, mapping exactly onto the Substack subheads — so no new type, no new review surface, no schema. **(D5)** extraction is licensed **only** because it terminates in a human review gate ([[llm-vs-determinism-surface-boundary]]), and it **may not invent**: it selects and structures text present on the page, never supplies a missing quantity or infers an unlisted ingredient — the same fidelity-first rule that made ADR-0032 reject letting the model read the URL itself; a gap returns **as a gap**. **(D6)** provenance is a **priority rung, not a code path** — `RecipeAttributeVotes` already ranks chrome 0 / microdata 1 / jsonLD 2, so LLM scalars enter **below chrome** and any deterministic value wins automatically; plus a declared `ModelCall` at the ADR-0043 chokepoint. **(D7)** budget for thinking *and* output and **throw on truncation** — `maxTokens` is shared with reasoning ([[reasoning-budget-starves-output]]) and a half-finished recipe must never pass as a parse ([ADR-0040](ADR-0040-editable-at-the-grain-it-is-stored.md) lossless-or-loud). **Honest about the cost:** this puts the first model call in the app's highest-cost-of-error path (a bad capture becomes a recipe you cook from), mitigated structurally rather than carefully — it runs only where determinism produced *nothing*, can never outrank a deterministic source, and cannot commit anything; capture also stops being fully offline **on no-contract pages only**. **Ratified same-day with all five OQs closed:** **frontier tier by default** ("I'll happily pay to get it right") — the **mirror image of ADR-0035**, whose classifier is on-device *by design* because it is high-volume/low-stakes/re-runnable, where this is low-volume and high-stakes; "by default" is literal, so ADR-0045 D7's model setting and degradation still apply (OQ1). The **share extension does not escalate** — it captures and stores as today and the *app* escalates on draft-open, which is binding on design because `WebRecipePageParser.parse` is **pure and synchronous**: the gate sits at the existing async boundary reading the warnings the pure parser returned, so the ladder gains a rung *above* the parser, never inside it (OQ2). **Whole-page extraction, not per-gap** — the priority ladder discards deterministic halves automatically, making it safe by construction rather than by careful prompt scoping (OQ3). **Re-run is offered** off the retained `originalHTML`, so a retry costs a model call and no re-fetch and still works on a page captured while authenticated (OQ4). **Per-site extractors stay allowed** — the fallback is the **floor, not the ceiling**: bespoke code stays faster/free/offline/deterministic for high-volume sites, and the fallback's job is to make *not* writing one non-blocking, so a per-site extractor becomes an optimization taken on evidence rather than a prerequisite for capturing at all (OQ5). S1 serializer + gate + whole-page call (fixture-tested: the Samin page, a contract-bearing page asserting the model is **not** called, a partial page asserting deterministic halves survive), S2 review-surface provenance + re-run, S3 selection-to-field parked; extends ADR-0007/0009; no schema (**Accepted 2026-07-26 — S1 dispatchable**)
- [ADR-0048](ADR-0048-playbook-edit-grain.md) — **Playbook edit affordances are a readout of storage grain, not chrome drift; Serve With decomposes to rows.** The dogfood report ("Learnings seems most mature … Chef it Up is a singular edit panel … Reader Feedback requires an explicit edit tap and then strange scrollable Text Edit windows") reads as UI inconsistency and is not: each section's affordance accurately reflects how it is stored, and the maturity ranking Jon intuited **is** the grain ranking — Learnings and Reader Feedback are real rows (`learnings`, `recipeNotes`), Serve With is a JSON blob, Make Ahead and Chef It Up are single strings. **Three findings drive it.** (1) **Serve With has row identity and no row**: `ServeWithItem` is `Identifiable` with a `UUID` but lives in `Recipe.serveWith: Data?`, and the codebase is *already paying* — `reconciledServeWithItems` exists solely to carry UUIDs across a whole-blob rewrite by matching on `title == && note ==`, so editing an item's title silently mints a new UUID and drops the old identity, invisibly and unrecoverably. (2) **Make Ahead and Chef It Up only *look* like lists**: `PlaybookEnrichmentDisplayText` splits multi-line strings into bullets at render time, so the surface promises a list the storage can't keep — the single-panel editor is telling the truth and the *renderer* is the liar. (3) **`ServeWithCoding.decode` swallows failures** (`(try? …) ?? []`), presenting a corrupt blob as "no items" — a lossless-or-loud violation sitting on the read path any migration would use. **(D1)** do **not** unify by making the chrome uniform — row-style affordances over blob storage would decode/mutate/rewrite the whole blob and reintroduce the prep-plan defect in four places at once; **unify the grain and the affordances follow**. **(D2)** extract the Learnings interaction (inline edit, swipe delete, `onMove`) into one shared component that **Reader Feedback adopts immediately** — already rows, so its Edit tap and scrollable `TextEditor` are pure UI artifact; schema-free, and most of what was actually asked for. **(D3)** Serve With decomposes to a **`recipeServeWith`** table — deletes `reconciledServeWithItems` outright, makes per-item edits sync-granular instead of whole-blob last-writer-wins, and gets **its own typed home** rather than being stuffed into the generic `learnings` table ([[decompose-notes-into-typed-homes]]). **(D4)** Make Ahead and Chef It Up **stay prose** — no per-item identity, no per-item consumer, nothing anchored to their lines; decomposing them would be schema built on a newline split. Revisit only when a real consumer appears (a Make Ahead line becoming a prep-plan step, which is ADR-0034 territory). **(D5)** the loud decode ships **independent of** and **ahead of** D3, because it is the migration's own read path. **Cost:** one new synced table — cheap against ~30 already registered ([[synced-table-cost-calibration]]) and explicitly **not orphaned**, since its consumer ships in the same effort; pre-prod is the reason to do it now, the same call ADR-0042 OQ2 made for `workbenchLog`. S1 shared row editor (no schema), S2 loud decode, S3 Serve With → rows + migration, S4 Make Ahead/Chef It Up **deferred by D4, not scheduled**. **Both schema OQs closed same-day, and they turn out to be one design rather than two:** `recipeServeWith` **carries provenance but not `LearningProvenance`** — that enum is `{externalHandoff, inApp}`, which distinguishes the *transport* a learning arrived through (both cases are model paths), where Serve With needs **authorship**, model-suggested vs hand-typed; reusing it would record `inApp` for a hand-authored item and answer the wrong question (OQ2 — and the same conflation is noted, unfixed, in `Learning` itself). `sortOrder` is **sparse**, reusing `LearningOrdering.rankStride` (1024), so a reorder updates only moved rows across synced devices (OQ3). **The consequence built in from both:** because Serve With is *also* regenerated wholesale by the verb, the regeneration path must **upsert by identity and preserve hand-authored rows and their ranks** — a delete-and-reinsert would reproduce exactly the identity loss D3 exists to remove, and provenance is what makes "which rows are the cook's" answerable at all; that is S3's primary test, not a detail. Two implementation checks stay open inside their slices (Reader Feedback's multi-line bodies possibly weakening D2's single shared component → S1; ADR-0021 variation write-capture → S3); governed by ADR-0040, lives in ADR-0039, continues ADR-0041 (**Accepted 2026-07-26 — S1/S2 dispatchable**)
